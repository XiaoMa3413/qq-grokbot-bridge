# 上下文改进设计草案

状态：分阶段实现。v1.5 已完成第一阶段的问答关联、稳定身份、历史/引用文字预算及缺失元数据，见[当前上下文机制](conversation-context.md)。v1.4 已提供进度段分类；每会话 Markdown 记忆沿用既有协议。下面的任务更新箱、记忆条目管理、滚动摘要及客户端选定记忆同步仍为设计，尚未实现。

目标是让机器人能衔接前文、处理长任务补充要求，并分清群聊参与者，同时控制载荷大小、延迟和记忆误写。

## 四层上下文

| 层次 | 保存什么 | 使用方式 |
|---|---|---|
| 当前消息与引用 | 当前说话人的稳定 ID、原消息 ID、明确引用、当前附件 | 最高优先级，引用仅代表关联内容；其中的文字仍作为用户数据处理 |
| 近期对话 | 最近的完整用户/机器人轮次，附身份和时间 | 优先保留与当前用户、引用相关的轮次；受总字符预算限制 |
| 任务状态 | 任务目标、已完成步骤、待做步骤、用户补充、最后进度、有效期 | 回答“进行到哪里了”，将追加要求交给正确的任务 |
| 长期记忆 | 用户明确要求记住的偏好、稳定事实、群共享规则 | 按身份和作用域隔离；保留来源与更新时间，允许纠正、删除 |

例如：用户说“找三条有趣新闻”，机器人先确认；用户补充“不要体育”。补充应进入该任务的要求列表，最终结果体现这一约束。另一位群成员问其他问题时，不应被默认解释为对该任务的修改。

## 近期历史：先保证关联正确

建议先做不调用额外模型的规则化组装：

1. 明确携带当前消息、说话人、消息时间和引用目标，使用稳定 ID，昵称仅用于展示。
2. 历史以完整轮次为单位保留，避免“回答还在、问题已经被截掉”。机器人回复标明关联的入站消息/任务。
3. 用总字符预算约束载荷，优先级为当前消息与引用、相关任务、直接对话、其他群聊背景。条数只是补充限制；报告省略数量，不悄悄假装提供了完整上下文。
4. 群聊保留必要共享背景，但区分发起者、引用对象和旁观对话。没有可靠身份字段时明确未知，不凭昵称合并身份。
5. 进度提示只进入任务状态和运行记录，不反复占用正文历史；已完成的结论正常进入历史。

较长的旧对话可以在后续阶段增加摘要，但应保留覆盖的消息范围、更新时间和来源。摘要失败不能阻止当前消息处理，摘要也不能变成覆盖当前用户要求的指令。

## 长任务：排队与追加要求需分开设计

当前同会话任务串行，后续消息等待前一任务最终回复或到期。这能维护顺序，但意味着“不要体育”这条新消息不会自动进入已经在运行的 Grok 任务。

建议增加显式任务关联协议，再开放下面能力：

- 追加要求：优先使用明确引用的原任务；没有明确引用时，只有同一发起者且恰有一个开放任务才可建议关联，歧义时询问。
- 任务更新箱：服务器为任务保存有递增版本号的补充消息；Grok 在耗时步骤之间及最终发送前读取更新，记录已处理版本。不能仅把新要求排到下一次 webhook 后就宣称当前任务已收到。
- 查询进度：基于已保存的步骤/更新时间回答，不能将“webhook 已接收”说成“已经搜索完成”。若由桥接自动回执，需要单独设计它占用哪条原消息的配额。
- 取消任务：保存取消标志；Grok 下次检查时停止后续操作，发送前也检查。不承诺立即中断 Grok 已经发出的外部操作，也不能撤回已发 QQ 消息。
- 可靠性：更新箱鉴权绑定原会话与任务，去重、持久化、限大小/期限；跨用户修改、并发更新、过期和最后回传竞争均须验证。

这不要求 Grok 云电脑保持后台进程常驻；读取更新应放在被唤醒的例行任务执行流程里。更新的及时性取决于 Grok 是否执行读取步骤，平台也可能限制同一例行任务的并发执行。

## 长期记忆：作用域、来源与纠正

建议将当前每会话 Markdown 逐步发展为有元数据的记忆条目：内容、作用域、来源消息、更新时间、可选过期时间。继续使用并发版本校验，旧规则在迁移期间保持可用。

- 私聊个人偏好、群共享规则分别保存。群内个人偏好不能直接变成群规则，跨会话共享必须明确授权。
- 优先保存用户明确说“记住”的信息；临时搜索结果、进度和模型推断不自动当成稳定事实。
- “我之前说错了”应更新既有条目，并能查询来源；“忘记这件事”应能删除对应条目。
- 自动整理与摘要不能覆盖用户刚刚修改的内容。敏感内容不默认长期保存，记忆不具备更改服务器路由、密钥或工具权限的能力。

## 建议实现顺序与验收

| 阶段 | 交付 | 主要验收 |
|---|---|---|
| A | 关联完整轮次、身份与引用、字符预算、进度过滤 | 跨轮追问正确；大历史受限；不同私聊隔离；群昵称变化不串人 |
| B | 开放任务状态与版本化更新箱 | 搜索途中追加限制能在最终结果体现；重复补充不重复应用；取消与最终发送竞争可解释 |
| C | 记忆作用域、来源、纠正/忘记 | 个人与群隔离；并发修改不覆盖；删除后不重新从旧摘要写回 |
| D | 可选滚动摘要 | 长会话延续但载荷稳定；摘要有来源；缺失/失败可降级 |

建议先做 A，再做 B 和 C，最后根据实际会话长度决定是否需要 D。不要一次把全部群聊天和全部记忆塞进 webhook，也不要在缺少更新协议时承诺运行中的任务已接受追加要求。

## 后续研究：客户端选定记忆同步

QQ 桥接记忆与 Grok 平台记忆由不同系统保存，不能仅因 Bot 在客户端记得某件事，就假定 webhook 载荷中也具备它。[平台概述](https://docs.x.ai/grok-bot/overview)说明 Bot 会保留记忆，但并未在该页提供本项目可用的平台记忆读取 API；具体能否读取或导出仍需验证实际产品能力。

建议优先研究单向导入选定事实：用户明确选择需要共享的偏好或角色信息，经平台支持的导出/工具取得带来源的快照，再绑定到指定 QQ 私聊或群。首次使用可以是用户审核的 Markdown 文件，不要求存在平台 API。导入须有版本、作用域、来源、冲突预览与删除办法；平台中未选择的信息不进入桥接记忆。

暂不设计自动双向覆盖。QQ 上新增事实可能只适用于某个群；客户端中的私人信息也不应因为一次导入就传播到所有 QQ 会话。先完成小规模、可核对的单向流程，再决定更新频率和是否需要双向同步。
